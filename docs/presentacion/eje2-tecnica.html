Eje 2 · Desarrollo y calidad

Cómo se estructura el servicio en Java / Spring Boot, qué se prueba, cómo se asegura la calidad y cómo se usa y se verifica la IA en la construcción.

Diseño propuesto: la implementación de referencia está en .NET 10 y fue verificada. La versión Java reutiliza los mismos contratos, tópicos, migraciones y reglas; los fragmentos de esta página muestran cómo quedaría y todavía no están compilados en el repositorio.

Estructura

  • Hexagonal con módulos Maven: la regla de dependencias la impone el compilador
  • Dominio en Java puro, sin Spring
  • Spring solo en los bordes (hosts e infraestructura)

Pruebas y calidad

  • JUnit 5 + AssertJ, falsos escritos a mano
  • Testcontainers con Kafka y PostgreSQL reales
  • ArchUnit, contrato OpenAPI, JaCoCo, compuertas en CI

IA en la construcción

  • El agente trabaja con reglas escritas (AGENTS.md)
  • Mismas compuertas que el código humano
  • Verificación contra el sistema real, obligatoria

01Estructura del servicio en Java / Spring

Un proyecto Maven con 7 módulos. Las flechas del pom.xml son la arquitectura: si el dominio no tiene Spring en su classpath, no puede usarlo aunque alguien quiera.

Reglas de diseño

  • El dominio y la aplicación no conocen Spring. Los casos de uso son clases normales; se crean con @Bean en cada host (composition root). Se prueban sin levantar contexto.
  • Interfaces sin prefijo I (convención Java): PublicadorEventos, implementado por PublicadorKafka.
  • Código síncrono sobre hilos virtuales (Java 21+) en lugar de async/await: la misma concurrencia con código más simple de leer y probar.
  • Inmutabilidad: record para eventos, contratos y resultados; Guia con campos privados y sin setters.
  • Resultados explícitos (enum + switch exhaustivo) en lugar de excepciones para el flujo normal: APLICADO, DUPLICADO, TARDIO, TRANSICION_INVALIDA.
  • Configuración 100 % por variables de entorno (@ConfigurationProperties validadas al arrancar).

03Código clave (del centro hacia afuera)

Los mismos nombres y reglas que en .NET. Primero el dominio, que es Java puro; después el caso de uso y el decorador; por último Spring, en el borde.

tcc-dominio · Guia.java

/** Única que decide si un evento cambia su estado. Sin setters. */
public final class Guia {
  private final String numeroGuia;
  private EstadoGuia estadoActual;
  private OffsetDateTime ultimoEventoEn;
  private long version;

  public static Guia crear(EventoGuia primero) {
    return new Guia(primero.numeroGuia(), primero.estado(), primero.ocurridoEn(), 1);
  }

  public ResultadoAplicacion aplicar(EventoGuia evento) {
    if (!evento.numeroGuia().equals(numeroGuia))
      throw new IllegalArgumentException("Evento de otra guía");
    if (evento.ocurridoEn().isBefore(ultimoEventoEn))
      return ResultadoAplicacion.TARDIO;          // no retrocede
    if (!MaquinaEstados.puedeTransitar(estadoActual, evento.estado()))
      return ResultadoAplicacion.TRANSICION_INVALIDA;
    estadoActual = evento.estado();
    ultimoEventoEn = evento.ocurridoEn();
    version++;
    return ResultadoAplicacion.APLICADO;
  }
}

tcc-aplicacion · RecibirEvento.java

/** Deja el evento guardado de forma durable. Sin Spring. */
public final class RecibirEvento {
  private final PublicadorEventos publicador;
  private final FiltroDuplicados filtro;

  public RecibirEvento(PublicadorEventos publicador, FiltroDuplicados filtro) {
    this.publicador = publicador;
    this.filtro = filtro;
  }

  public ResultadoRecepcion ejecutar(EventoGuia evento) {
    if (filtro.yaRecibido(evento.idEvento()))
      return ResultadoRecepcion.DUPLICADO;
    publicador.publicar(evento);
    // Se marca DESPUÉS de publicar: si la publicación falla,
    // el reintento del emisor no se descarta como duplicado.
    filtro.marcarRecibido(evento.idEvento());
    return ResultadoRecepcion.ACEPTADO;
  }
}

tcc-aplicacion · PublicadorConContingencia.java (patrón Decorador)

/** Nunca 202 sin almacenamiento durable: si nadie lo guarda, falla (→ 503). */
public final class PublicadorConContingencia implements PublicadorEventos {
  private final PublicadorEventos principal;
  private final AlmacenContingencia contingencia;

  @Override
  public void publicar(EventoGuia evento) {
    try {
      principal.publicar(evento);
      return;
    } catch (PublicacionFallidaException e) {
      log.debug("Kafka no disponible; {} a contingencia", evento.idEvento(), e);
    }
    try {
      contingencia.guardar(evento);
    } catch (RuntimeException e) {
      throw new PublicacionFallidaException(
          "Ni Kafka ni la contingencia guardaron " + evento.idEvento(), e);
    }
  }
}

tcc-api · ConfiguracionRecepcion.java (composition root)

// Spring solo arma el grafo; el orden de los decoradores queda a la vista:
// Contingencia( Circuito( Kafka ) )
@Configuration
class ConfiguracionRecepcion {

  @Bean
  RecibirEvento recibirEvento(ProductorKafka productor, CircuitBreaker circuito,
                              AlmacenContingenciaJdbc contingencia,
                              FiltroDuplicadosRedis redis) {
    PublicadorEventos kafka = new PublicadorKafka(productor);
    PublicadorEventos conCircuito = new PublicadorConCircuito(kafka, circuito);
    PublicadorEventos publicador = new PublicadorConContingencia(conCircuito, contingencia);
    FiltroDuplicados filtro = new FiltroDuplicadosTolerante(redis);  // Redis caído ≠ 503
    return new RecibirEvento(publicador, filtro);
  }
}

tcc-api · EventosGuiaController.java

@RestController
@RequestMapping("/api/v1/eventos-guia")
class EventosGuiaController {

  @PostMapping
  @PreAuthorize("hasAuthority('SCOPE_eventos:escribir')")
  ResponseEntity<Void> recibir(@Valid @RequestBody EventoGuiaV1 cuerpo,
                               JwtAuthenticationToken token) {
    autorizador.verificarOrigen(token, cuerpo.origen()); // 403 si suplanta
    return switch (recibirEvento.ejecutar(Mapeador.aDominio(cuerpo))) {
      case ACEPTADO  -> ResponseEntity.accepted().build(); // 202 durable
      case DUPLICADO -> ResponseEntity.ok().build();       // 200 sin efecto
    };
  }
}

tcc-infraestructura · RepositorioGuiasJdbc.java (inbox + estado + outbox)

@Override
public void guardar(Guia guia, EventoGuia evento, ResultadoAplicacion resultado,
                   EstadoGuia estadoAnterior) {
  transaccion.executeWithoutResult(tx -> {
    int historial = jdbc.sql("""
        INSERT INTO historial_eventos (id_evento, numero_guia, estado, ocurrido_en,
                                       origen, novedad, resultado)
        VALUES (:id, :guia, :estado, :ocurrido, :origen, :novedad, :resultado)
        ON CONFLICT (id_evento) DO NOTHING""")
        .params(parametros(evento, resultado)).update();
    if (historial != 1) throw new ConflictoConcurrenciaException(guia.numeroGuia());
    if (resultado != APLICADO) return;             // tardío/inválido: solo historial

    int filas = estadoAnterior == null
        ? insertarGuia(guia)                             // ON CONFLICT DO NOTHING
        : actualizarGuia(guia);                          // WHERE version = :anterior
    if (filas != 1) throw new ConflictoConcurrenciaException(guia.numeroGuia());

    insertarEnBandejaSalida(guia, evento, estadoAnterior);  // outbox, misma tx
  });                                                    // excepción ⇒ rollback de todo
}

En .NET las tres escrituras viajan en un solo NpgsqlBatch; en Java son tres sentencias en la misma transacción (o un batch JDBC con reWriteBatchedInserts). La garantía la dan las llaves primarias y la versión, no el viaje a la base.

04Kafka en Spring: consumo, reintentos y DLQ

Spring Kafka ya trae los patrones que en .NET se construyeron a mano. Se usan sin cambiar los nombres de tópicos ni grupos, para que .NET y Java sean intercambiables.

tcc-procesador · reintento bloqueante (el orden es sagrado)

@KafkaListener(topics = "guias.eventos.recibidos", groupId = "procesador-estado",
               concurrency = "${procesador.hilos:6}")  // ≤ particiones asignadas
void procesar(ConsumerRecord<String, String> registro, Acknowledgment ack) {
  procesarEvento.ejecutar(lector.leer(registro));  // ilegible ⇒ MensajeInvalidoException
  ack.acknowledge();                               // offset DESPUÉS del commit en la base
}

@Bean
DefaultErrorHandler manejoErrores(DeadLetterPublishingRecoverer dlq) {
  var espera = new ExponentialBackOff(200, 2.0);
  espera.setMaxInterval(30_000);                   // sin límite de intentos:
  var manejador = new DefaultErrorHandler(dlq, espera); // la base caída se espera
  manejador.addNotRetryableExceptions(MensajeInvalidoException.class); // poison ⇒ DLQ
  return manejador;
}

Cada hilo del contenedor es dueño de sus particiones: se conserva el orden por guía y las particiones avanzan en paralelo, que es lo que hace DespachadorParticiones en .NET. Asignación cooperative-sticky y commits manuales.

tcc-notificador · reintento no bloqueante (el flujo es sagrado)

// Escalera explícita con los mismos tópicos que .NET:
// guias.estados.cambiados → notificaciones.reintento.1m → .10m → .1h
//                         → canal alterno (correo) → notificaciones.dlq
@KafkaListener(topics = {"notificaciones.reintento.1m",
                          "notificaciones.reintento.10m",
                          "notificaciones.reintento.1h"},
               groupId = "notificador-reintentos")
void reintentar(ConsumerRecord<String, String> registro, Acknowledgment ack) {
  var mensaje = lector.leer(registro);
  esperarHasta(mensaje.reintentarEn());           // pausa la partición, no el hilo
  switch (notificar.ejecutar(mensaje)) {
    case ENVIADO, YA_ENVIADO, OBSOLETO -> { }       // idempotencia guía:versión:canal
    case PROVEEDOR_CAIDO -> enrutador.siguienteEtapa(mensaje);
  }
  ack.acknowledge();
}

Spring Kafka ofrece @RetryableTopic, que hace lo mismo con tópicos generados. Se prefiere el enrutador explícito para conservar los nombres de tópicos y grupos de .NET: así ambas versiones pueden convivir durante la migración.

Productor

  • acks=all, enable.idempotence=true
  • Clave = numeroGuia (orden por guía)
  • send().get(timeout): el 202 espera la confirmación

Relay del outbox

  • @Scheduled + pg_try_advisory_xact_lock: un solo líder
  • Publica en orden de version y marca en la misma tx
  • Restaura el contexto de traza guardado en la fila

Observabilidad

  • Agente OpenTelemetry: HTTP, JDBC y Kafka sin código
  • Métricas tcc_* con Micrometer (mismos nombres)
  • Logs JSON con trace_id hacia Loki

05Qué probaría y cómo

La pirámide de la versión .NET se porta tal cual. Las pruebas se escriben primero en Java y funcionan como la especificación de la migración.

NivelHerramientaQué garantiza.NET

Las imprescindibles

  • 50 procesamientos concurrentes del mismo evento → 1 fila (PostgreSQL real)
  • Conflicto de versión entre escrituras → rollback completo
  • Kafka caído → contingencia; Kafka y base caídos → 503
  • Poison pill → DLQ sin congelar la partición
  • Dos relays a la vez → sin duplicados ni desorden

06Cómo aseguro la calidad

La calidad no depende de la memoria ni de la buena voluntad: está en compuertas automáticas que nadie puede saltarse, más una revisión humana que se enfoca en lo que las máquinas no ven.

1 · En la máquina

  • javac -Werror + Error Prone
  • Formato con Spotless
  • mvn verify antes del push

2 · En el PR

  • Todas las pruebas + Testcontainers
  • ArchUnit y contrato OpenAPI
  • JaCoCo: cobertura de líneas nuevas
  • Sonar: sin nuevos problemas

3 · Seguridad

  • Dependencias vulnerables (OWASP / Trivy)
  • Secretos en el código (Trivy)
  • Imagen distroless escaneada

4 · Sistema completo

  • Prueba de humo con las imágenes reales
  • Staging + aprobación
  • Canary 10 % → 100 %

Definición de terminado

  • Toda corrección de bug trae la prueba que lo reproduce
  • Cambio de esquema = nueva migración expand/contract; nunca editar una aplicada
  • Contrato V1 solo con cambios compatibles; si no, V2 conviviendo
  • Decisión relevante = ADR en el mismo PR
  • Métricas y logs para lo nuevo (si no se ve, no está terminado)

Qué mira la revisión humana

  • Garantías: ¿hay algún camino que responda 202 sin durabilidad? ¿el offset se confirma antes de tiempo?
  • Concurrencia: ¿comprobar-y-actuar sin llave única? ¿estado compartido entre hilos?
  • Fallas: ¿excepciones tragadas? ¿reintentos sin límite donde no deben?
  • Seguridad y datos: ¿datos personales en logs o en el evento?
  • Diseño: ¿cabe en la hexagonal? ¿nombre claro? ¿una sola responsabilidad?

SOLID aplicado: responsabilidad única (un caso de uso por clase), abierto/cerrado (decoradores), sustitución (cualquier adaptador cumple el puerto), segregación (puertos pequeños y específicos), inversión de dependencias (la aplicación define las interfaces que la infraestructura implementa).

07IA y agentes en la construcción

La versión .NET se construyó con un agente de código, paso a paso. La lección: el agente acelera, pero la verificación sigue siendo obligatoria.

Cómo lo uso

  • Andamiaje y código repetitivo (adaptadores, mapeos, configuración)
  • Pruebas: casos límite que a una persona se le pasan
  • Migración .NET → Java: las pruebas portadas son la especificación y el agente implementa hasta que pasan
  • Revisión de PR como segunda mirada, no como aprobador
  • Documentación y ADR a partir del código real

Cómo lo verifico

  • Reglas escritas para el agente (AGENTS.md): capas, nombres, contratos, secretos
  • Pasos pequeños: un cambio, una prueba, un commit
  • Mismas compuertas que el código humano: pruebas, ArchUnit, contrato, seguridad
  • Verificación contra el sistema real (Docker, carga, caos), no solo en memoria
  • Quien abre el PR responde por el código y debe poder explicarlo

Lo que la verificación atrapó

  • El límite de tamaño del cuerpo se ignoraba en un caso
  • localhost resolvía a IPv6 y los servicios no se veían
  • Fechas no UTC: 28 eventos válidos a la DLQ (recuperados con replay)
  • El procesador era el cuello de botella (90 → 343 ev/s tras corregirlo)
  • Tokens JWT colados en los resultados de k6 antes de publicarlos

Reglas del equipo

  • Nada de secretos ni datos reales en los prompts
  • Se miden resultados (lead time, fallas en producción), no líneas generadas
  • Riesgo principal: aceptar código que no se entiende → pairing y revisiones que piden explicar el porqué

IA en la operación (fuera del camino crítico)

  • Agente de novedades: consume con su propio grupo y actúa por la misma API, con su cliente OAuth2
  • Autonomía según el riesgo: reprogramar = automático; devolver = aprueba una persona
  • Si el agente falla, la ingesta, el estado y las notificaciones siguen

08Preparación para el ejercicio de código

Un ejemplo de revisión de un fragmento con errores típicos del dominio y la versión corregida. El método es el mismo para cualquier fragmento: leer, preguntar, probar, cambiar.

Fragmento a revisar

@KafkaListener(topics = "guias.eventos.recibidos")
public void procesar(String json, Acknowledgment ack) {
  ack.acknowledge();                                        // 1
  try {
    EventoGuia e = mapper.readValue(json, EventoGuia.class);
    log.info("Evento {} tel {}", e, cliente.telefono()); // 2
    if (!repo.existeEvento(e.idEvento())) {              // 3
      Guia g = repo.obtener(e.numeroGuia());
      g.setEstado(e.estado());                             // 4
      repo.guardar(g);
      kafka.send("guias.estados.cambiados", g);         // 5
      repo.guardarHistorial(e);
    }
  } catch (Exception ex) {                                 // 6
    ex.printStackTrace();
  }
}

Hallazgos

1Offset antes de procesar: si el proceso muere, el evento se pierde. Confirmar después del commit en la base.
2Dato personal en logs (Ley 1581). El evento no debe traer teléfono y los logs se enmascaran.
3Comprobar y luego actuar: dos hilos pasan el if a la vez. La garantía es la llave primaria del inbox (ON CONFLICT) dentro de la transacción.
4Setter que salta la máquina de estados: no valida transición ni tardíos, y no controla la versión. Debe ser guia.aplicar(evento). Además g puede ser null (primera vez).
5Doble escritura: publica en Kafka fuera de la transacción y antes del historial. Si falla entre medias, hay anuncio sin estado o estado sin anuncio. Solución: outbox en la misma transacción.
6Excepción tragada: un error transitorio (base caída) se pierde en silencio. Los transitorios se reintentan; los ilegibles van a la DLQ.

Versión corregida

@KafkaListener(topics = "guias.eventos.recibidos", groupId = "procesador-estado")
void procesar(ConsumerRecord<String, String> registro, Acknowledgment ack) {
  EventoGuia evento = lector.leer(registro);   // ilegible ⇒ DLQ
  procesarEvento.ejecutar(evento);             // inbox+estado+outbox, 1 tx
  ack.acknowledge();                           // solo tras el commit
}                                              // transitorios: se reintenta

La lógica sale del listener: el caso de uso decide con la máquina de estados y el repositorio garantiza "todo o nada". El listener queda en cuatro líneas y se prueba por separado.

Si el ejercicio es programar

  1. Preguntar antes de escribir: ¿puede llegar repetido? ¿desordenado? ¿qué pasa si falla a la mitad?
  2. Empezar por la prueba del caso feliz y de un caso límite (duplicado, tardío, transición inválida).
  3. Dominio primero, sin frameworks: una clase con reglas y resultados explícitos.
  4. Nombrar las garantías en voz alta: idempotencia, atomicidad, orden.
  5. Cerrar con lo que falta: qué probaría después y qué cambiaría con más tiempo.

Ejercicio probable: implementar MaquinaEstados.puedeTransitar o Guia.aplicar con sus pruebas, o revisar un consumidor o un endpoint como el de arriba.
